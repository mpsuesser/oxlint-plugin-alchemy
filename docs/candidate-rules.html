Rank 1 · v1 migration footgun

no-v1-await-resource

Ban await Cloudflare.R2Bucket(...), await AWS.Lambda.Function(...), etc. v2 resources are Effects — use yield* inside an Alchemy.Stack generator.

Leverage: high Confidence: med-high Tier 1

Why it matters

In v1, every resource constructor returned a Promise: const bucket = await R2Bucket("bucket", {}). In v2 the same constructor returns an Effect. await-ing it kicks off no work, races no deploy, and silently leaves you with an unfinalized Effect value being used as if it were a resource handle. The next code that reads bucket.bucketName gets undefined behavior, and there is no diagnostic until something tries to use the (non-)Output downstream.

Cases this would catch
// v1 leftover — silently produces an unfinalized Effect, not a resource.
const bucket = await Cloudflare.R2Bucket("Bucket");

const queue = await AWS.SQS.Queue("Jobs", { fifoQueue: true });

const fn = await AWS.Lambda.Function("Api", { main: "./api.ts" });
Allowed
// v2 — yield* inside a Stack / Worker / Effect.gen.
Effect.gen(function* () {
    const bucket = yield* Cloudflare.R2Bucket("Bucket");
    const queue  = yield* AWS.SQS.Queue("Jobs");
});

Implementation sketch

import type { ESTree } from 'effect-oxlint';
import * as Effect   from 'effect/Effect';
import * as Option   from 'effect/Option';
import { AST, Diagnostic, Rule, RuleContext } from 'effect-oxlint';

const ALCHEMY_ROOTS = new Set(['Cloudflare', 'AWS', 'Alchemy', 'Axiom', 'PlanetScale']);
const PASCAL = /^[A-Z][A-Za-z0-9]*$/;

export default Rule.define({
    name: 'no-v1-await-resource',
    meta: Rule.meta({ type: 'problem', description: '...' }),
    create: function* () {
        const ctx = yield* RuleContext;
        return {
            AwaitExpression: (node) => {
                const a = node as ESTree.AwaitExpression;
                if (a.argument.type !== 'CallExpression') return Effect.void;
                const call = a.argument;
                if (call.callee.type !== 'MemberExpression') return Effect.void;
                const path = AST.memberPath(call.callee);
                if (Option.isNone(path)) return Effect.void;
                const root  = path.value[0];
                const final = path.value[path.value.length - 1];
                if (!ALCHEMY_ROOTS.has(root)) return Effect.void;
                if (!PASCAL.test(final))   return Effect.void;
                return ctx.report(Diagnostic.make({
                    node,
                    message: `v1 \`await ${path.value.join('.')}(...)\` is not supported in v2 — use \`yield* …\` inside Alchemy.Stack. (AL-3)`
                }));
            }
        };
    }
});

AST shape: AwaitExpression → CallExpression → MemberExpression chain. Reuses the namespace allowlist and PascalCase predicate from require-stable-logical-id; safe to extract into a shared util.ts when these duplicate.

Verdict: Strongest argument to ship next. Pure migration-aid value; same heuristic stack as the existing require-stable-logical-id rule; almost zero novel design.
Rank 2 · v1 migration footgun

no-shouty-binding-keys

In a Platform's bindings: { ... } object, ban SHOUTY_SNAKE_CASE keys — v2 uses PascalCase shorthand matching the resource identifier.

Leverage: high Confidence: med-high Tier 1

Why it matters

v1 convention was bindings: { BUCKET: bucket } and the Worker handler read env.BUCKET. v2 standardizes on bindings: { Bucket } — the key is the same identifier as the resource, accessed as env.Bucket. InferEnv derives the typed shape from this naming. A migrated codebase that keeps the old keys ends up with mismatched InferEnv output and confusing autocomplete.

Cases this would catch
export const Worker = Cloudflare.Worker("Worker", {
    main: "./src/worker.ts",
    bindings: { BUCKET: Bucket, KV: Sessions }   // ← flag both
});
Allowed
export const Worker = Cloudflare.Worker("Worker", {
    main: "./src/worker.ts",
    bindings: { Bucket, Sessions }                  // ← canonical shorthand
});

Implementation sketch

import type { ESTree } from 'effect-oxlint';
import * as Effect from 'effect/Effect';
import { AST, Diagnostic, Rule, RuleContext } from 'effect-oxlint';

// Two-deep platform identifiers — extend as new platforms ship.
const PLATFORMS: ReadonlyArray<readonly [string, string]> = [
    ['Cloudflare', 'Worker'],
    ['Cloudflare', 'Container'],
];
const SHOUTY = /^[A-Z][A-Z0-9_]*$/;

export default Rule.define({
    name: 'no-shouty-binding-keys',
    meta: Rule.meta({ type: 'suggestion', description: '...' }),
    create: function* () {
        const ctx = yield* RuleContext;
        return {
            CallExpression: (node) => Effect.gen(function* () {
                const call = node as ESTree.CallExpression;
                if (!PLATFORMS.some(([o, p]) => AST.isCallOf(call, o, p))) return;

                for (const arg of call.arguments) {
                    if (arg.type !== 'ObjectExpression') continue;
                    for (const prop of arg.properties) {
                        if (prop.type !== 'Property') continue;
                        if (prop.key.type !== 'Identifier') continue;
                        if (prop.key.name !== 'bindings') continue;
                        if (prop.value.type !== 'ObjectExpression') continue;

                        for (const binding of prop.value.properties) {
                            if (binding.type !== 'Property') continue;
                            if (binding.key.type !== 'Identifier') continue;
                            if (!SHOUTY.test(binding.key.name)) continue;
                            yield* ctx.report(Diagnostic.make({
                                node: binding.key,
                                message: `v1 \`${binding.key.name}\` binding key — use shorthand \`{ ${...} }\` matching the resource class for InferEnv to derive correctly. (AL-6)`
                            }));
                        }
                    }
                }
            })
        };
    }
});
Verdict: Strongly recommend shipping. Med-high confidence comes from the slight risk that someone genuinely wants a SHOUTY env var key — but the docs go out of their way to deprecate that style, and the rule is auto-fixable to shorthand whenever the value is a PascalCase identifier.
Rank 3 · v1 migration footgun

no-v1-entrypoint-prop

Disallow entrypoint: in a Worker / Lambda / Container props object — renamed to main: in v2.

Leverage: med-high Confidence: med Tier 1

Why it matters

A direct rename. Passing entrypoint: in v2 silently does nothing because the prop isn't read — and depending on TS settings, an excess property check may not even fire (e.g. when the props are spread or come from a variable). Result: deploy goes through with the wrong bundle. This is the rename most likely to bite during a v1→v2 sweep.

Cases this would catch
Cloudflare.Worker("Worker", {
    entrypoint: "./src/worker.ts",   // ← flag
    bindings: { Bucket }
});
Allowed
Cloudflare.Worker("Worker", {
    main: "./src/worker.ts",
    bindings: { Bucket }
});

Implementation sketch

import type { ESTree } from 'effect-oxlint';
import * as Effect from 'effect/Effect';
import { AST, Diagnostic, Rule, RuleContext } from 'effect-oxlint';

const PLATFORMS: ReadonlyArray<readonly [string, string]> = [
    ['Cloudflare', 'Worker'],
    ['Cloudflare', 'Container'],
];

export default Rule.define({
    name: 'no-v1-entrypoint-prop',
    meta: Rule.meta({ type: 'problem', description: '...' }),
    create: function* () {
        const ctx = yield* RuleContext;
        return {
            CallExpression: (node) => {
                const call = node as ESTree.CallExpression;
                const matches = PLATFORMS.some(([o, p]) => AST.isCallOf(call, o, p));
                if (!matches) return Effect.void;

                for (const arg of call.arguments) {
                    if (arg.type !== 'ObjectExpression') continue;
                    for (const prop of arg.properties) {
                        if (prop.type !== 'Property') continue;
                        if (prop.key.type !== 'Identifier') continue;
                        if (prop.key.name !== 'entrypoint') continue;
                        return ctx.report(Diagnostic.make({
                            node: prop.key,
                            message: '`entrypoint:` was renamed to `main:` in Alchemy v2. (AL-5)'
                        }));
                    }
                }
                return Effect.void;
            }
        };
    }
});
Verdict: Ship. Tight scope, easy auto-fix, narrowly targeted to platforms so false positives on unrelated entrypoint: keys are impossible.
Rank 4 · v1 migration footgun

no-v1-finalize

Ban app.finalize() / await app.finalize() — v2 lifecycle is handled by the Alchemy.Stack wrapper.

Leverage: med Confidence: med Tier 1

Why it matters

In v1, every alchemy.run.ts ended with await app.finalize() to flush the deploy. v2's Alchemy.Stack(...) wraps the lifecycle and there is no .finalize() to call. A leftover call either crashes (no such method on the new return type) or silently no-ops on a stale typing.

Cases this would catch
const app = await alchemy("my-app", {});       // also flagged by no-v1-await-stack
// ...
await app.finalize();                       // ← this rule
Allowed
// v2 — Alchemy.Stack handles finalization internally.
export default Alchemy.Stack("MyApp", {...}, Effect.gen(function* () {...}));

Implementation sketch

// Match `x.finalize()` where `x` is a bare identifier — narrow to reduce
// false positives on unrelated `.finalize()` methods (e.g. crypto APIs).
export default Rule.define({
    name: 'no-v1-finalize',
    meta: Rule.meta({ type: 'problem', description: '...' }),
    create: function* () {
        const ctx = yield* RuleContext;
        return {
            CallExpression: (node) => {
                const call = node as ESTree.CallExpression;
                if (call.callee.type !== 'MemberExpression')   return Effect.void;
                const m = call.callee;
                if (m.computed)                                return Effect.void;
                if (m.property.type !== 'Identifier')        return Effect.void;
                if (m.property.name !== 'finalize')           return Effect.void;
                if (m.object.type !== 'Identifier')          return Effect.void;
                if (call.arguments.length !== 0)             return Effect.void;
                return ctx.report(Diagnostic.make({
                    node,
                    message: 'v1 `app.finalize()` is not needed in v2 — `Alchemy.Stack(...)` finalizes automatically. (AL-2)'
                }));
            }
        };
    }
});

Heuristic: require obj.finalize() with zero arguments and a bare identifier object. Could be tightened with scope analysis (only flag when obj was bound from alchemy(...)), but the bare-identifier + zero-arg shape is rare outside the v1 pattern.

Verdict: Ship. Companion to no-v1-await-stack; together they're the "definitely a v1 codebase" smoke alarm.
Rank 5 · Output safety

no-string-concat-output

Ban string concatenation and untagged template literals that interpolate Output-shaped values — use Output.interpolate.

Leverage: high Confidence: med (heuristic) / high (with type info) Tier 3

Why it matters

An Output<string> is a lazy reference, not a string. Concatenating one with template literals or + calls toString() on the lazy expression node, producing garbage like "prefix-[object Object]/objects/*". This goes into deployed config and is found later by humans staring at a broken ARN. Output.interpolate\`...\` is a drop-in fix that wires dependencies correctly.

Cases this would catch (heuristically) 
const bucket = yield* Cloudflare.R2Bucket("Bucket");

const arn = `arn:aws:s3:::${bucket.bucketName}/objects/*`;   // ← flag
const dsn = "postgres://" + db.host + ":" + db.port;       // ← flag
Allowed
const arn = Output.interpolate`arn:aws:s3:::${bucket.bucketName}/objects/*`;
const dsn = Output.interpolate`postgres://${db.host}:${db.port}`;

Implementation sketch

// Heuristic: an interpolated expression looks Output-shaped if it is a
// MemberExpression whose property name ends in a recognized Output suffix.
const OUTPUT_SUFFIX = /(Name|Url|Arn|Id|Endpoint|Host|Region|Port|Key)$/;

const looksLikeOutput = (node: ESTree.Expression): boolean => {
    if (node.type !== 'MemberExpression') return false;
    if (node.computed) return false;
    if (node.property.type !== 'Identifier') return false;
    return OUTPUT_SUFFIX.test(node.property.name);
};

export default Rule.define({
    name: 'no-string-concat-output',
    meta: Rule.meta({ type: 'suggestion', description: '...' }),
    create: function* () {
        const ctx = yield* RuleContext;
        return {
            TemplateLiteral: (node) => {
                const t = node as ESTree.TemplateLiteral;
                // Skip if parent is a TaggedTemplateExpression with tag `Output.interpolate`.
                if (t.parent?.type === 'TaggedTemplateExpression') return Effect.void;
                if (t.expressions.some(looksLikeOutput)) {
                    return ctx.report(Diagnostic.make({
                        node, message: 'Use `Output.interpolate\`...\`` — concatenating an Output stringifies the lazy expression. (AL-11)'
                    }));
                }
                return Effect.void;
            },
            BinaryExpression: (node) => {
                const b = node as ESTree.BinaryExpression;
                if (b.operator !== '+') return Effect.void;
                if (looksLikeOutput(b.left) || looksLikeOutput(b.right)) {
                    return ctx.report(Diagnostic.make({
                        node, message: '... (AL-11)'
                    }));
                }
                return Effect.void;
            }
        };
    }
});

The suffix list is the soft point. False positives are likely on user code where .someName isn't actually an Output. Recommend shipping behind an opt-in "hardcore" preset, or expose a config option for the suffix list. A type-aware implementation (resolve the expression's declared type and look for Output<…>) would be the proper fix and is on the roadmap for effect-oxlint's typeAware mode.

Verdict: High leverage, real-world bug-finder, but ship after the four Tier-1 rules and consider gating behind hardcore: true in plugin options until type-aware support lands.
Rank 6 · phase discipline

bind-in-init-only

Disallow Resource.bind(...) calls inside a Worker / Lambda's per-request fetch: handler. Bindings belong in the outer init Effect.

Leverage: high Confidence: med Tier 2

Why it matters

The init/exec phase split is load-bearing in v2: Binding.Policy only runs at plantime, Binding.Service ships in the runtime bundle. Calling .bind() in the per-request handler defeats the whole model — it tries to look up the Policy layer in a context that doesn't have it (runtime), and even when it falls back to Service, you've moved one-time SDK setup into the hot path of every request.

Cases this would catch
Cloudflare.Worker("Worker", { main: import.meta.path },
    Effect.gen(function* () {
        return {
            fetch: Effect.gen(function* () {
                const bucket = yield* Cloudflare.R2Bucket.bind(Bucket);  // ← flag
                return HttpServerResponse.text("hi");
            }),
        };
    }),
);
Allowed
Cloudflare.Worker("Worker", { main: import.meta.path },
    Effect.gen(function* () {
        const bucket = yield* Cloudflare.R2Bucket.bind(Bucket);   // ← init phase
        return {
            fetch: Effect.gen(function* () {
                return HttpServerResponse.text("hi");
            }),
        };
    }),
);

Implementation sketch

// Strategy:
//   1. Visit `*.bind(...)` CallExpressions.
//   2. Walk ancestors. Find the nearest enclosing function-shaped node
//      (FunctionExpression / ArrowFunctionExpression / function*).
//   3. If that function is the value of a Property whose key is `fetch`,
//      and that Property lives inside an ObjectExpression returned from
//      another Effect.gen — flag it.

import { AST, Diagnostic, Rule, RuleContext } from 'effect-oxlint';

export default Rule.define({
    name: 'bind-in-init-only',
    meta: Rule.meta({ type: 'problem', description: '...' }),
    create: function* () {
        const ctx = yield* RuleContext;
        return {
            CallExpression: (node) => {
                const call = node as ESTree.CallExpression;
                if (call.callee.type !== 'MemberExpression') return Effect.void;
                if (call.callee.property.type !== 'Identifier') return Effect.void;
                if (call.callee.property.name !== 'bind') return Effect.void;

                // Walk ancestors looking for `Property{ key.name = 'fetch' }` value.
                let cursor: ESTree.Node | undefined = node.parent;
                while (cursor !== undefined) {
                    if (cursor.type === 'Property'
                     && cursor.key.type === 'Identifier'
                     && cursor.key.name === 'fetch') {
                        return ctx.report(Diagnostic.make({
                            node,
                            message: '`.bind()` belongs in the outer init Effect, not inside the per-request `fetch:` handler. (AL-9)'
                        }));
                    }
                    cursor = cursor.parent;
                }
                return Effect.void;
            }
        };
    }
});

Ancestor walking via the .parent chain that oxlint synthesizes (same trick avoid-any uses for double-cast detection). Refinement to reduce false positives on unrelated .bind() calls (e.g. Function.prototype.bind inside a fetch:): require the callee object to be a MemberExpression rooted in a known Alchemy namespace.

Verdict: High leverage and the cleanest "you've misunderstood the framework" diagnostic in the whole list. The ancestor walk is the only non-trivial bit — recommend implementing once the simpler rules ship.
Rank 7 · structure

platform-main-import-meta-path-when-collocated

When a file export defaults a Platform constructor, its main: should be import.meta.path.

Leverage: low Confidence: med Tier 4

Why it matters

The collocated-platform pattern (one file = one Worker, infra + runtime side by side) is the canonical v2 layout. The tell is main: import.meta.path: it lets you move the file around without updating any path string. A hardcoded "./src/worker.ts" in a file that is ./src/worker.ts works today but breaks the moment the file is moved or renamed.

Cases this would catch
// src/worker.ts
export default Cloudflare.Worker("Worker", {
    main: "./src/worker.ts",                        // ← flag
}, Effect.gen(function* () { ... }));
Allowed
// src/worker.ts
export default Cloudflare.Worker("Worker", {
    main: import.meta.path,
}, Effect.gen(function* () { ... }));

Implementation sketch

// Visit ExportDefaultDeclaration whose declaration is a Platform call.
// Find the props object (2nd arg). If `main:` value is a string literal
// (not `import.meta.path`), flag it.

const isImportMetaPath = (expr: ESTree.Expression): boolean => {
    if (expr.type !== 'MemberExpression') return false;
    if (expr.computed) return false;
    if (expr.property.type !== 'Identifier' || expr.property.name !== 'path') return false;
    return expr.object.type === 'MetaProperty';   // import.meta
};
Verdict: Nice-to-have. Skip unless you find yourself moving Worker files around a lot. The "wrong" form continues to work — it's purely a refactor-resilience nudge.
Rank 8 · naming

no-shadowing-global-worker

Warn when Worker is imported as a named import or declared locally — the global Worker (Web Worker) collides.

Leverage: low-med Confidence: med Tier 2

Why it matters

Cloudflare Workers run in a Web-Worker-shaped runtime where Worker is a global constructor. A named import import { Worker } from "alchemy/Cloudflare" shadows it locally, and inside the Worker code you can no longer reference the global. In practice the prefer-namespace-imports rule already steers people away from this, but a targeted message helps catch local class declarations that happen to be named Worker.

Cases this would catch
import { Worker } from "alchemy/Cloudflare";   // ← flag (also caught by AL-8)
class Worker { ... }                              // ← flag in any file importing alchemy/Cloudflare
Allowed
import * as Cloudflare from "alchemy/Cloudflare";
Cloudflare.Worker("Worker", ...);
Verdict: Mostly subsumed by prefer-namespace-imports (AL-8). Skip as a standalone rule; consider folding the message into AL-8's diagnostic when the named identifier happens to be Worker.
Rank 9 · Output safety

no-console-log-output

Warn on console.log(resource.attr) where the value is an Output — logs [Output] instead of the resolved value.

Leverage: low-med Confidence: low-med Tier 3

Why it matters

Debugging console.log(bucket.bucketName) shows [Output] rather than the resolved name, because the value is a lazy reference. The right pattern is to return { bucketName } from the Stack — outputs print at the end of alchemy deploy — or to pipe(Output.map(console.log)). The Effect plugin's existing use-console-service rule already covers console.* usage broadly, so this is a redundant narrower variant.

Cases this would catch (heuristically) 
const bucket = yield* Cloudflare.R2Bucket("Bucket");
console.log(bucket.bucketName);              // prints "[Output]"
Allowed
// Return outputs from the Stack generator — alchemy prints them after deploy.
return { bucketName: bucket.bucketName };
Verdict: Skip. Too much overlap with oxlint-plugin-effect's use-console-service, low blast radius (mistake surfaces in dev on first run), and the heuristic is no more accurate than no-string-concat-output's. Revisit if a type-aware engine lands.

Rules already shipped: no-v1-await-stack, no-v1-import-paths, require-stable-logical-id, prefer-namespace-imports, stack-in-alchemy-run-file. See src/rules/ and test/rules/ for the working implementations and the test patterns they all share.
